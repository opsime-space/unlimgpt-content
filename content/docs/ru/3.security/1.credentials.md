UnlimGPT разделяет следующие границы доступа. Перед отзывом доступа с потерянного устройства проверьте их в [Настройках](/ru/settings) выбранного аккаунта и организации.

- **Способы входа** связывают Google или адрес почты и пароль с одним аккаунтом.
- **Ключи доступа (passkeys)** — аутентификаторы: например, Touch ID или аппаратный ключ безопасности.
- **Сессии браузера** показывают браузеры и устройства, где выполнен вход; каждую сессию можно отозвать.
- **Разрешения CLI** — отдельные разрешения OAuth с правами, сроком действия и группой токенов обновления.
- **API-ключи** авторизуют приложения и инструменты разработки; у каждого ключа свой жизненный цикл.

Ключ доступа или второй фактор подтверждает шаг входа, но не заменяет API-ключ в HTTP-запросе. Разрешение OAuth для CLI позволяет ему выполнять операции с аккаунтом, а настроенный AI-клиент использует отдельный API-ключ организации. Именно организация ключа определяет тариф и кредиты для вызова, даже если в другой вкладке браузера выбрана иная организация.

## Выберите нужный отзыв

При потере браузера завершите его сессию. При потере компьютера с CLI проверьте авторизацию CLI и API-ключи, сохранённые для клиентов. Текущий список авторизаций показывает общее имя CLI и даты, но не надёжное имя устройства; если несколько доступов нельзя сопоставить с потерянным компьютером, отзовите **все** авторизации CLI и войдите заново только на доверенных устройствах. При раскрытии ключа приложения отзовите именно этот ключ и создайте замену. Это отдельные действия: отзыв одного API-ключа не завершает сессии браузера, а завершение сессии не удаляет ключ приложения. Порядок восстановления описан в [безопасности аккаунта](/ru/docs/account/security).

Если исходное устройство недоступно, начните сдерживание с другого доверенного устройства. Найдите имя и маску затронутого ключа в [API-ключах](/ru/api-keys), отзовите раскрытое значение, выпустите замену и проверьте её бесплатным каталогом моделей. Обновите все нагрузки старого ключа. Затем отдельно проверьте оставшиеся сессии браузера и доступы CLI: смена пароля сама по себе не доказывает их отзыв.

## Храните и проверяйте учётные данные

Полные локальные API-ключи и токен обновления CLI хранятся в системном хранилище учётных данных. Конфигурационные файлы содержат только адреса, ID моделей, имена профилей и команды получения ключа. Полное значение ключа показывается один раз при создании; позднее [список API-ключей](/ru/docs/account/api-keys) показывает метаданные. Проверьте замену бесплатным [каталогом моделей](/ru/docs/api/models) до платного вызова и убедитесь, что старый ключ неактивен.

Для ключа, созданного в браузере, вы сами выбираете доверенное место для одноразового значения. Для ключа, созданного через CLI, проверьте, что операция поддерживается [установленным выпуском](/ru/docs/cli/install): CLI хранит полное значение в системном хранилище, а в профиле оставляет только ID. Ручное подключение внешнего клиента может передать ключ через буфер обмена в его секретное поле — хранение этого клиента тоже входит в границу доступа.

Не помещайте ключи, токены, cookie и содержимое запросов в репозитории, логи, URL и обращения в поддержку. [Приватность данных разработчика](/ru/docs/security/privacy) перечисляет безопасные диагностические поля. [Безопасность CLI](/ru/docs/cli/security) объясняет передачу локальных секретов и осторожный откат конфигурации.
