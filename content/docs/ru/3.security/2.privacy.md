[Политика конфиденциальности](/ru/privacy) — источник утверждённых сроков хранения и юридических обязательств. Это руководство описывает рабочие действия: какие идентификаторы помогают разобрать вызов, как не раскрыть содержимое и что делать при утечке credentials. Оно не вводит отдельного обещания о хранении.

## Просматривайте активность без содержимого

Войдите в организацию, которой принадлежит ключ, и откройте [активность API](/ru/api-activity). Список показывает модель, endpoint, исход, длительность, входные и выходные токены, окончательное списание кредитов и ID запуска. ID запуска отличается от HTTP-заголовка `request-id`; при сопоставлении клиентской и кабинетной записи храните их отдельно. Активность не показывает prompts, responses, полные API-ключи, имя ключа и закрытые сведения об исполнении. Полный секрет появляется только один раз при создании в [API-ключах](/ru/api-keys); затем список показывает метаданные. Доступ к активности одной организации не следует считать доступом к записям другой.

Строка активности — диагностическая запись; она не означает, что содержимое нигде не существует. Web-чат сохраняет сообщения беседы. Для Responses по умолчанию действует `store: true`: очищенный ответ может сохраняться для последующего чтения. Явное `store: false` запрещает последующее чтение завершённого ответа по ID. Во время генерации запрос, привязанный к сохраняемой беседе, всё ещё может показывать частичный ответ по этому ID и добавлять элементы беседы. При явном `Idempotency-Key` терминальный payload может сохраняться для безопасного повтора даже с `store: false`; безопасные метаданные операции и учёта записываются в любом случае. При выборе хранения смотрите [правила API](/ru/docs/api/responses), [идемпотентность](/ru/docs/api/idempotency-and-retries) и [Политику конфиденциальности](/ru/privacy).

## Подготовьте обращение в поддержку

Запишите время с часовым поясом, endpoint, публичный ID модели при необходимости, HTTP `request-id`, безопасный код ошибки и признак потока. Эти значения помогают отличить сбой транспорта от отказа API. Не прикладывайте тело запроса, сгенерированный ответ, API-ключ, cookie браузера, OAuth-token, значение системного хранилища CLI, полный вывод окружения и сырую внутреннюю ошибку. Перед отправкой скриншота или консольного лога удалите чувствительные данные приложения. [Ошибки и лимиты](/ru/docs/api/errors-and-limits) помогут прочитать публичный код.

В клиентском журнале оставляйте только эти разрешённые поля; никогда не логируйте заголовок авторизации и полные объекты запроса или ответа. Скриншот терминала может содержать историю команд, содержимое буфера обмена и локальные пути: проверьте весь кадр до отправки. Если лог нельзя надёжно очистить, опишите статус и код словами.

## Отреагируйте на раскрытие

Если ключ попал в репозиторий, лог, задачу или скриншот, считайте его раскрытым. Отзовите затронутый ключ, создайте замену, обновите его клиентов и бесплатно проверьте её через [каталог моделей](/ru/docs/api/models). Отдельно проверьте сессии браузера и доступы CLI по [безопасности аккаунта](/ru/docs/account/security): это другие credentials. Не вставляйте раскрытое значение в обращение как доказательство; используйте безопасные метаданные или ID ключа из списка.

Если секрет был встроен в развёрнутую конфигурацию, замените его в утверждённом хранилище секретов и перезапустите либо обновите затронутую нагрузку обычным порядком изменений. Удаление строки из репозитория не делает уже скопированный ключ безопасным. До завершения инцидента проверьте, что старый ключ неактивен, а следующий вызов клиента проходит с заменой.

О сроках хранения, правах на удаление и юридических подробностях читайте [Политику конфиденциальности](/ru/privacy). Доступные поля операций перечислены в [руководстве по активности](/ru/docs/account/usage).
